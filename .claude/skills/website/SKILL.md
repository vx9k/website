# Working on kthread.dev

`AGENTS.md` holds the rules (brief, content, accessibility, security, code
style); read it first and let it win over anything here. This skill is the
procedures: what to run, in what order, and what to check. Do the work in
this one session; there's no need for subagents on a site this size.

## Where things are

- Copy and data: `src/app/content.ts`, nothing else. The page
  (`src/app/page.tsx`), the Markdown version (`src/app/index.md/route.ts`)
  and the JSON-LD all read from it, so a new field on `Product` usually
  needs all three updated.
- One product: `src/components/site/Product.tsx`. Sections:
  `src/components/site/Section.tsx`. Tokens and utilities:
  `src/app/globals.css`.
- Headers and CSP: `public/_headers`, filled in by `scripts/csp.mjs` after
  `next build`. The `/` Worker: `src/worker.ts`.

## Adding or updating a product

1. Read the repository, not memory: `gh api repos/<owner>/<repo>/readme -H
   'Accept: application/vnd.github.raw'`, the manifest (`Cargo.toml`,
   `package.json`, `build.zig.zon`, `CMakeLists.txt`), the license and the
   latest release (`gh api repos/<owner>/<repo>/releases`).
2. For group work (an org such as Poopware Laboratories), check vx's part
   with `gh api repos/<owner>/<repo>/contributors` and set `group` with an
   accurate `role` ("main contributor", "contributor"). Don't list a
   group's repos that are mostly someone else's work.
3. Fill the `Product` fields: `summary` is one sentence; `notes` are two or
   three specifics from the README, one sentence each; `status` uses the
   repo's own words ("experimental", "early days"); `license` is the SPDX
   id. Avoid version numbers in `status` for repos that release daily.
4. Order `products` by how much each says about vx's work.
5. Screenshot, only from the repo or vx. Download into the scratchpad,
   look at it, then convert:

   ```sh
   for w in 640 1280; do
     magick shot.png -filter Lanczos -resize ${w}x /tmp/s$w.png
     avifenc -q 70 -s 4 /tmp/s$w.png public/work/<id>-$w.avif
     magick /tmp/s$w.png -quality 82 public/work/<id>-$w.webp
   done
   ```

   Set `image.width`/`height` to the 1280 file's size and write `alt` that
   says what the screenshot shows.
6. Run new copy past the content rules in `AGENTS.md`: plain, sentence
   case, no em dashes, no marketing words, only checkable claims. Units
   like `MB/s` can break at the slash on phones; a word joiner
   (`MB/⁠s`) keeps them whole.
7. Update the product list in `AGENTS.md` ("Today's are ...").

## Verifying a change

1. `pnpm build`. It runs `next build` and then `scripts/csp.mjs`.
   - If `next build` stops with a Next.js security advisory, the installed
     Next has a known vulnerability: update `next` and
     `eslint-config-next` together.
   - `csp.mjs` joins each run of adjacent inline scripts (Next.js's
     streamed `self.__next_f.push` data) into one before hashing, because
     how many there are depends on the machine's streams. It should print
     a handful of hashes; if it ever reports a line over 2,000 characters,
     look at what new inline scripts the page has gained.
   - `pnpm exec tsc --noEmit` before a build complains about `LayoutProps`;
     those types are generated by `next build`, so ignore it.
2. Look at it. `pnpm wrangler dev` serves `out/` as production does
   (restart it after each build). For screenshots without a browser
   session, serve `out/` and use headless Firefox at both widths:

   ```sh
   python3 -m http.server 8765 -d out &
   firefox --headless --profile "$(mktemp -d)" --no-remote --window-size=1440,3000 --screenshot desk.png http://localhost:8765/
   firefox --headless --profile "$(mktemp -d)" --no-remote --window-size=390,5200 --screenshot phone.png http://localhost:8765/
   ```

   Lazy images show as their alt text in these shots; that's expected.
3. Check `/index.md` reads correctly (`curl localhost:8765/index.md`).
4. With a real browser and `pnpm wrangler dev`, open `/` and a missing path
   with the console open: no CSP or Trusted Types errors.

## Dependencies

Dependabot opens one PR per package, and each rewrites `pnpm-lock.yaml`,
so merging them one by one conflicts. Instead, on a branch:

```sh
pnpm add next@<v> react@<v> react-dom@<v>          # react and react-dom always match
pnpm add -D eslint@^<v> eslint-config-next@<v> ... # eslint-config-next tracks next
pnpm build
```

Open one PR that says `Closes #n` for each Dependabot PR, wait for
Workers Builds to pass, and merge; GitHub closes the others. `pnpm lint`
stays broken until typescript-eslint supports TypeScript 7. Keep wrangler's
`compatibility_date` no newer than the bundled `workerd`.

## Shipping

Branch from `main`, commit with a short imperative summary and a body
that explains why, push, and open a PR with `gh pr create`. Workers Builds
builds every branch; `main` deploys to kthread.dev on merge. Merge only
when vx asks.
